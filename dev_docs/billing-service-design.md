# Биллинг-сервис для AI-продуктов — дизайн

Статус: черновик v1 · 2026-11-15

Отдельный сервис аккаунтов, подписок, кредитов, квот и рефералов для продуктов
**TyCo**, **FastCat**, **BloggerDog** и будущих. Идеи и часть кода берём из
биллинга BloggerDog (`apps/api/src/modules/billing`, `ai-usage`, `referrals`,
Prisma-модели `Plan…PartnerPayout`), но совместимость с ним не цель: сервис
проектируется как самостоятельный продукт, к которому BloggerDog подключается
так же, как остальные.

---

## 1. Цели и не-цели

### Цели

1. Один сервис обслуживает любое число продуктов. Новый продукт подключается
   конфигурацией (продукт, тарифы, ключи API), без изменения кода ядра.
2. Продаём **подписки**, **пакеты кредитов** и **дисковую квоту**. Тарифы
   гибкие: версии, акционные и скрытые тарифы, архив.
3. Точный учёт себестоимости AI (LLM, STT, изображения, видео, перевод) и
   перевод её в кредиты по формуле, а не по таблице «операция → цена».
4. Деньги принимает Merchant of Record (Paddle или Polar), а в мобильных
   приложениях — App Store и Google Play. Все источники оплаты дают одни и те
   же права.
5. Реферальная программа: сначала награда кредитами и подписками, денежные
   выплаты позже, но модель данных готова к ним с первого дня.
6. Изоляция: BloggerDog работает на своём экземпляре (своя БД, свой аккаунт
   MoR); TyCo и FastCat — на общем, с общим логином.

### Не-цели

- Выставление счетов, расчёт налогов, хранение карт — это делает MoR или магазин.
- Маршрутизация запросов к моделям и их выполнение — это AI-шлюз на
  `@bozonx/ai-kit` (см. §9). Биллинг только оценивает, резервирует и списывает.
- Денежные выплаты партнёрам в v1 (только учёт начислений, §12.4).
- Внешние биллинг-движки (Lago, Flexprice) и LiteLLM не используем: метеринг
  и цены уже есть в `ai-kit` и в моделях BloggerDog, а внешний движок добавил
  бы второй источник правды и сетевой переход в горячем пути `reserve`.

## 2. Ключевые правила (инварианты)

1. **MoR и магазины — источник правды по деньгам и статусу оплаты.** Сервис
   никогда сам не считает, сколько клиент заплатил; он реагирует на
   идемпотентные вебхуки и периодически сверяется с API провайдера.
2. **Сервис — источник правды по правам, балансам и квотам.** Продукты не
   хранят собственных копий прав дольше кэша с TTL и никогда не пишут в журнал
   кредитов.
3. **Журнал кредитов только дописывается.** Баланс — сумма записей. Исправление —
   новая запись (отрицательная или компенсирующая), никогда не правка старой.
4. **Деньги — целые числа в микроединицах** (`1_000_000 = 1 USD`), тип `BigInt`.
   Кредиты — целые числа.
5. **Каждая операция, меняющая состояние, идемпотентна** по ключу, который
   передаёт вызывающая сторона (`Idempotency-Key`).
6. **Версии неизменяемы.** Версия тарифа, версия цены модели, версия условий
   реферальной программы после публикации не редактируются; изменение — новая
   версия. Подписки и события ссылаются на версию, по которой были созданы.
7. **Бизнес-логика читает права, а не коды тарифов.** Никаких `if plan === 'pro'`.
8. **Учёт потребления — только на сервере.** Клиентские приложения (Tauri,
   браузер, мобильные) никогда не сообщают о расходе сами.

## 3. Термины

| Термин | Значение |
| --- | --- |
| **Deployment** (экземпляр) | Отдельный запуск сервиса со своей БД и своими аккаунтами MoR. Пример: `ivan-apps` (TyCo + FastCat), `bloggerdog`. |
| **Product** | Продукт внутри экземпляра: `tyco`, `fastcat`, `bloggerdog`. Свои тарифы, свои кошельки кредитов, свои права. |
| **Identity** (пользователь) | Человек с логином. Есть только в экземплярах, где включён модуль аккаунтов (§5). |
| **BillingAccount** | Тот, кто платит и чьи балансы. Принадлежит пользователю (личный) или организации продукта (командный). |
| **Plan / PlanVersion** | Тариф и его неизменяемая коммерческая версия: цена, период, права, начисление кредитов. |
| **Offer** | Как версия тарифа продаётся через конкретный источник оплаты: price id в Paddle/Polar, product id в App Store/Google Play. |
| **Entitlement** | Право: ключ → значение (`int`, `bool`, `enum`). Реестр ключей свой у каждого продукта. |
| **Subscription** | Оплаченная подписка на версию тарифа через источник оплаты. |
| **Grant** | Права или кредиты, выданные без оплаты: акция, реферал, компенсация, бета-тестер. |
| **Credit bucket** | Партия кредитов одного происхождения и срока жизни в кошельке продукта. |
| **Hold** | Резерв кредитов под операцию, которая ещё выполняется. |
| **Meter** | Единица измерения потребления: `input_tokens`, `audio_seconds`, `images`, `storage_bytes`… |

## 4. Архитектура

```
              ┌───────────── экземпляр ivan-apps ─────────────┐
TyCo (Tauri) ─┤                                               │
FastCat (web, │  billing-api (NestJS)  ←→  Postgres           │
  native)    ─┤      │   ▲                    ▲               │
              │      │   │ S2S API             │               │
AI-шлюз ──────┼──────┘   │                     │               │
 (ai-kit)     │      billing-worker (BullMQ) ──┘  Redis        │
              │      billing-web (Nuxt): портал клиента,       │
              │                       checkout, админка        │
              └──────────────▲──────────────────────────────────┘
                             │ вебхуки
          Paddle / Polar · App Store Server Notifications · Google RTDN

              ┌───────────── экземпляр bloggerdog ────────────┐
BloggerDog ───┤  тот же код, своя БД, свой аккаунт MoR,       │
              │  модуль аккаунтов выключен (свой auth)        │
              └───────────────────────────────────────────────┘
```

### 4.1. Стек

Как в BloggerDog: **Node.js 24, TypeScript, NestJS 11, Prisma, PostgreSQL,
BullMQ + Redis, Nuxt 4 + Vue 3** для веба, pnpm + turbo монорепо.

### 4.2. Структура репозитория

```
apps/
  api/        NestJS: HTTP API (публичный, S2S, вебхуки)
  worker/     NestJS-приложение без HTTP: очереди, cron, сверки
  web/        Nuxt: портал клиента, checkout, страницы тарифов
  admin/      Nuxt: бэк-офис (тарифы, кредиты, клиенты, рефералы, деньги)
packages/
  core/       чистый домен: правила кредитов, тарифов, статусов (без IO)
  contracts/  типы и DTO API, коды ошибок, события — общие с SDK
  client/     SDK для продуктов (@billing/client): S2S-клиент, кэш прав,
              проверка подписи событий
  client-vue/ Vue-компоненты для встраивания: баланс, апгрейд, paywall
  pricing-sync/ скрипт обновления цен провайдеров (§10.4)
prisma/
dev_docs/
```

Домен в `packages/core` — чистые функции, как `domain/*.rules.ts` в BloggerDog
(`credit-spending.rules.ts`, `credit-pricing.rules.ts`,
`subscription-state.rules.ts`, `downgrade.rules.ts`). Их переносим почти
дословно, обобщив под продукты.

### 4.3. Почему отдельный сервис, а не библиотека

- Продукты разнородны: Tauri-приложение, Nuxt-сайт, мобильные приложения,
  NestJS-монолит. Общий для всех — только HTTP.
- Вебхуки MoR и магазинов приходят в одно место на экземпляр.
- Кросс-продуктовые вещи (бандлы, рефералы, общий логин) требуют одной БД.

Задержка `reserve` — один запрос к сервису в том же регионе плюс одна
транзакция Postgres. Для чтения прав SDK держит кэш (§13.3).

## 5. Аккаунты и мультиарендность

### 5.1. Модуль аккаунтов (опциональный на экземпляр)

- **Включён в `ivan-apps`.** Один логин для TyCo и FastCat: email + пароль,
  magic link, OAuth (Google, Apple — обязателен для iOS при наличии других
  OAuth). Продукты авторизуют пользователя через OIDC (authorization code +
  PKCE; для Tauri — loopback/deep link). Регистрация в FastCat при наличии
  аккаунта TyCo — это просто «Войти» и согласие с условиями FastCat.
- **Выключен в `bloggerdog`.** У BloggerDog свои пользователи и организации;
  он создаёт `BillingAccount` через S2S API с `externalRef = organizationId`.

Код аккаунтов берём из BloggerDog (`auth`, `UserSession`, `AuthIdentity`,
`VerificationToken`, `MailOutbox`), упрощённо.

### 5.2. BillingAccount

```
BillingAccount
  id, deploymentScope
  ownerType: 'user' | 'external'      -- user = Identity, external = сущность продукта
  ownerUserId?                         -- для личных
  productId?                           -- для external: чей это аккаунт
  externalRef?                         -- id организации в продукте
  country, currencyHint, email
  status: 'active' | 'suspended' | 'deleted'
```

- У пользователя в `ivan-apps` один личный `BillingAccount` на все продукты:
  одна история платежей, один клиент в MoR.
- Командные аккаунты (организации BloggerDog, будущие команды FastCat) —
  отдельные `BillingAccount` с местами (`seats`, логика из `seats.service.ts`).
- Покупатель в MoR (`providerCustomerId`) привязан к `BillingAccount`.

### 5.3. Кошельки и права — по продуктам

Балансы и права всегда разделены по продуктам: `(billingAccountId, productId)`.
Себестоимость токенов в продуктах разная, а объединить кошельки позже легко,
разделить — тяжело. Объединение — только через продукт: бандл-тариф (§7.4) и
перекрёстные гранты (§8.5).

## 6. Права (entitlements)

### 6.1. Реестр

Каждый продукт объявляет реестр прав в конфигурации (по образцу
`ENTITLEMENTS` из `entitlements.contracts.ts`): ключ, тип, значение по
умолчанию для бесплатного уровня, правило слияния.

```ts
// пример для tyco
{
  'ai.enabled':            { type: 'bool', default: false, merge: 'or' },
  'ai.model_tier':         { type: 'enum', values: ['basic','pro','top'], default: 'basic', merge: 'max' },
  'credits.monthly':       { type: 'int',  default: 0, merge: 'sum' },   // информативно, начисляет §8.3
  'sync.enabled':          { type: 'bool', default: false, merge: 'or' },
  'storage.quota_bytes':   { type: 'int',  default: 0, merge: 'sum' },
  'stt.live':              { type: 'bool', default: false, merge: 'or' },
  'byok.allowed':          { type: 'bool', default: false, merge: 'or' },
}
```

Реестр хранится в БД (`ProductEntitlementKey`) и редактируется из админки,
плюс экспортируется в `contracts` для типизации в продукте.

### 6.2. Вычисление эффективных прав

```
эффективные права (account, product) =
  default бесплатного уровня
  ⊕ права активных подписок, покрывающих продукт (включая бандлы)
  ⊕ права активных грантов тарифа (реферал, акция)
  ⊕ дополнения (storage add-on)
  ⊕ ручные переопределения (EntitlementOverride, из админки)
```

`⊕` — правило слияния ключа (`max`, `or`, `sum`, `override`). Статус подписки
влияет на вклад: `past_due` — полный, `read_only` — только ключи с флагом
`keepOnReadOnly`, `expired` — ничего (логика `entitlement.rules.ts`).

Результат кэшируется в Redis на `(account, product)` и сбрасывается событием
при любом изменении источников.

## 7. Каталог: тарифы, офферы, пакеты

### 7.1. Модель

```
Product            id, code, name, creditValueMicros, markupPolicyId, status
Plan               id, productScope[] (один или несколько продуктов), code, name,
                   kind: 'base' | 'addon' | 'bundle',
                   visibility: 'public' | 'unlisted' | 'archived', sortOrder
PlanVersion        id, planId, version, interval: 'month'|'year'|'lifetime',
                   trialDays, entitlements (по продуктам: { tyco: {...}, fastcat: {...} }),
                   creditGrants (по продуктам: { tyco: 3000 }), creditGrantPolicy,
                   effectiveFrom, effectiveTo, publishedAt
Offer              id, planVersionId, source: 'paddle'|'polar'|'app_store'|'google_play',
                   externalPriceId, amountMicros, currency, region?, isActive
CreditPack         id, productId, code, credits, validityDays, visibility
CreditPackOffer    id, creditPackId, source, externalPriceId, amountMicros, currency
Promotion          id, code, kind, rules, startsAt, endsAt, maxRedemptions
```

По сравнению с BloggerDog: цена вынесена из `PlanVersion` в `Offer`, потому
что одна версия продаётся по разной цене в Paddle, App Store (комиссия
15–30 %) и по регионам (PPP). Права у всех офферов одной версии одинаковые.

### 7.2. Жизненный цикл тарифа

- **public** — в прайс-листе, можно купить.
- **unlisted** — не в прайс-листе, покупается по прямой ссылке или выдаётся
  вручную: акции, early bird, спецклиенты, награды за рефералов.
- **archived** — купить нельзя; действующие подписки работают на своей версии
  до отмены (grandfathering без миграций, как в BloggerDog).
- Новая версия = новая строка. Переводить подписчиков на новую версию можно
  только явной операцией из админки с уведомлением клиентов (и, если меняется
  цена, через смену цены у MoR).

### 7.3. Акции

Два независимых механизма, не смешиваем:

- **Скидка на цену** — купон/скидка на стороне MoR (`Promotion.kind='discount'`
  хранит ссылку на discount id у провайдера). Магазины — промо-офферы
  Apple/Google.
- **Другое содержимое** — отдельная unlisted-версия тарифа или грант:
  больше кредитов, длинный триал, бонусный пакет к покупке
  (`Promotion.kind='grant'`, правило «при оплате X выдать Y»).

### 7.4. Бандлы

`Plan.kind='bundle'`, `productScope=['tyco','fastcat']`. Одна подписка у MoR,
права и начисление кредитов прописаны по каждому продукту. Подписка на бандл
и отдельная подписка на продукт могут сосуществовать; при покупке бандла
сервис предлагает отменить пересекающиеся подписки (proration — средствами MoR).

### 7.5. Дополнения (add-ons)

`Plan.kind='addon'` — регулярная покупка поверх базового тарифа: дополнительное
место на диске, дополнительные места в команде. Требует активного базового
тарифа того же продукта (`requiresBase`). Дисковая квота продаётся **только
как регулярное дополнение**, не разовым пакетом: хранение стоит денег каждый
месяц.

## 8. Кредиты

### 8.1. Что продаём

Клиент видит **кредиты**, а не токены. Курс кредита
(`Product.creditValueMicros`) и наценка задаются на продукт. Кредиты одного
продукта нельзя потратить в другом.

### 8.2. Модель

```
CreditBucket       id, accountId, productId,
                   kind: 'plan' | 'pack' | 'promo' | 'referral' | 'compensation' | 'trial',
                   granted, expiresAt?, sourceType, sourceId, createdAt
CreditLedgerEntry  id, accountId, productId, bucketId?, amount (+/-),
                   reason: 'accrual'|'purchase'|'consumption'|'expiry'|'refund'|
                           'adjustment'|'referral_reward'|'promo'|'transfer',
                   userId?, usageEventId?, paymentId?, holdId?,
                   idempotencyKey (unique), meta, createdAt
CreditHold         id, accountId, productId, userId?, feature, amount,
                   status: 'open'|'committed'|'released'|'expired',
                   expiresAt, idempotencyKey, createdAt
```

Отличие от BloggerDog: вместо двух кошельков `monthly`/`pack` — партии
(`CreditBucket`) с видом и сроком. Это позволяет добавлять реферальные,
акционные и компенсационные кредиты без новых кошельков. Остаток партии —
сумма записей журнала по ней (материализуется в `bucket_balances` триггером
или в той же транзакции для скорости чтения; источник правды — журнал).

### 8.3. Начисление

- **По тарифу** — в начале каждого оплаченного периода (по
  `currentPeriodStart`, не по календарю). Для годовых тарифов — ежемесячными
  порциями. Партия `plan`, сгорает в конце порции.
- **Пакеты** — при подтверждённой оплате. Партия `pack`, срок `validityDays`
  (по умолчанию 365).
- **Гранты** — акции, рефералы, компенсации: партия соответствующего вида со
  сроком из правила гранта.

### 8.4. Порядок списания

Из `credit-spending.rules.ts`, обобщённо: сначала партии, которые сгорают
раньше; при равенстве — `plan` → `trial` → `promo` → `referral` →
`compensation` → `pack`. Купленное тратится последним.

### 8.5. Перекрёстные гранты

Акция «купил TyCo Pro — получил 500 кредитов FastCat» — это правило
`Promotion`, которое по событию оплаты создаёт партию `promo` в кошельке
другого продукта. Переводов между кошельками клиентом нет.

### 8.6. Протокол reserve → commit/release

```
POST /v1/credits/holds          { accountId, productId, userId, feature,
                                  estimate: { usage vector | costMicros }, ttlSec }
  → 201 { holdId, credits }   |  402 CREDITS_EXHAUSTED  |  403 ENTITLEMENT_DENIED
POST /v1/credits/holds/:id/commit   { usage vector, provider cost?, usageEventId }
  → { charged, refunded }
POST /v1/credits/holds/:id/release  { reason }
```

- Резерв — верхняя оценка (как `estimateCredits`); после commit разница
  возвращается.
- Резерв и проверка лимитов (дневной лимит пользователя, лимит участника
  команды, глобальный предохранитель из `ai-usage.config.ts`) — в одной
  транзакции с `SELECT … FOR UPDATE` по строке кошелька.
- Незакрытые резервы закрывает воркер по `expiresAt` (release): упавший запрос
  клиенту ничего не стоит.
- Commit больше резерва (длинная генерация) списывает фактическое, баланс может
  уйти в минус максимум на разницу; следующий резерв будет отклонён, пока
  баланс не восстановится. Это лучше, чем обрывать ответ на середине.
- Для стриминга допускается частичный commit (`/extend`) на длинных сессиях
  (Gemini Live, Deepgram streaming): шлюз продлевает резерв каждые N секунд.

### 8.7. Автопополнение

Из `auto-top-up.service.ts`: выключено по умолчанию, обязательный месячный
потолок. Работает только для источников, которые позволяют списание без
участия клиента (MoR с сохранённым методом); в магазинах недоступно.

### 8.8. Возвраты

Возврат пакета через MoR → отрицательная запись на непотраченный остаток
партии. Если часть уже потрачена, остаток партии уходит в ноль, а разница
пишется в `meta` возврата для решения в админке (политика по умолчанию: в
минус не уводим, сумму фиксируем для антифрода).

## 9. Связь с AI-шлюзом

AI-шлюз — отдельный компонент (для TyCo/FastCat — общий сервис; BloggerDog —
модуль `ai-gateway`). Он на `@bozonx/ai-kit` выбирает модель и выполняет вызов.
Ключи провайдеров живут только в шлюзе.

Поток одного вызова:

1. Продукт → шлюз: запрос с токеном пользователя.
2. Шлюз → биллинг: права (`ai.enabled`, `ai.model_tier`) и `reserve` по оценке
   (входные токены известны, выход — `max_tokens`).
3. Шлюз → провайдер.
4. Шлюз → биллинг: `commit` с вектором потребления из ответа провайдера и
   `routeId`. Биллинг сам считает стоимость по своей таблице цен (§10) и пишет
   `UsageEvent`.
5. При ошибке провайдера — `release` (неудачный вызов не оплачивается клиентом,
   но `UsageEvent` со статусом `error` и нашей себестоимостью пишется всегда).

**Таблица цен в биллинге — источник правды по деньгам.** Каталог `ai-kit` —
для маршрутизации и оценки; цены в нём синхронизируются из биллинга (или из
общего источника, §10.4).

## 10. Себестоимость и метеринг

### 10.1. Вектор потребления

Вместо фиксированных колонок (`inputTokens`, `audioSeconds`… в `AiUsageEvent`)
— обобщённый вектор счётчиков:

```
meters: {
  input_tokens, output_tokens, cached_input_tokens, cache_write_tokens,
  reasoning_tokens, audio_input_tokens, audio_seconds, audio_seconds_realtime,
  diarization_seconds, characters, images, image_megapixels, video_seconds,
  web_searches, requests, neurons
}
```

`UsageEvent` хранит вектор (`jsonb`) и, для аналитики, основные счётчики
отдельными колонками. Плюс `costMicros`, `priceVersionId`, `creditsCharged`,
`provider`, `model`, `routeId`, `feature`, `status`, `traceId`, `rawUsage`
(исходное поле `usage` из ответа провайдера — для разбора спорных случаев).

### 10.2. Таблица цен

```
ModelRoute         id, provider, model, kind: 'llm'|'stt'|'tts'|'image'|'video'|'mt'|'embed'
RoutePriceVersion  id, routeId, version, effectiveFrom, effectiveTo,
                   source: 'manual'|'seed'|'sync'|'provider-api', approvedBy
RoutePriceItem     priceVersionId, meter, unitMicros, per (1 | 1e6 …),
                   tier? { fromContextTokens, … }, minBillableUnits?
```

Цена — набор строк «счётчик → цена за единицу», с поддержкой тиров
(у Gemini — дороже при контексте свыше 200k) и минимальной тарификации
(Groq STT — минимум 10 секунд). Новый тип модели не требует миграции схемы.

### 10.3. Правила расчёта

- Количество токенов — **только из ответа провайдера** (`usage`), никогда не
  своим токенизатором. Оценка своим токенизатором допустима только для резерва.
- **OpenRouter** — берём фактическую стоимость из ответа (`usage.cost`), а не
  пересчитываем по прайсу; цена в таблице нужна только для резерва.
- **Gemini** — токены размышления по цене выхода; аудиовход по своей цене;
  Live API — по токенам аудио (вход/выход раздельно); контекстный кэш —
  отдельные счётчики чтения и хранения.
- **Deepgram / Groq** — по секундам аудио с учётом минимума.
- **Cloudflare Workers AI** — в нейронах (`neurons`), курс нейрона — цена.
- **Изображения / видео** — по штукам, мегапикселям, секундам — как указано
  у провайдера.
- **Батч-API** — отдельный маршрут со своей ценой.

### 10.4. Обновление цен (`packages/pricing-sync`)

Cron раз в сутки:

1. Тянет цены из источников: API моделей OpenRouter (содержит цены), открытый
   файл цен LiteLLM (`model_prices_and_context_window.json`, используем как
   данные, без самого LiteLLM), models.dev, страницы цен провайдеров (парсер —
   только как подсказка).
2. Сравнивает с действующими `RoutePriceVersion`.
3. При расхождении создаёт **черновик** новой версии и уведомление в админку.
   Публикация — вручную. Автопубликация разрешена только для OpenRouter (там
   фактическая стоимость всё равно приходит в ответе).

### 10.5. Формула кредитов

Из `credit-pricing.rules.ts`:

```
credits = max(1, ceil(costMicros × markup / creditValueMicros))
```

`markup` — по ступеням стоимости модели (на дешёвых моделях выше, на топовых
ниже), политика на продукт (`MarkupPolicy`). Версия политики пишется в событие.

### 10.6. Сверка с провайдерами

Ежемесячно (и по запросу) воркер сравнивает сумму `costMicros` по провайдеру за
период со счётом провайдера (через billing/usage API, где есть: OpenAI,
Anthropic, OpenRouter, Google Cloud Billing export; иначе — ввод суммы в
админке). Расхождение больше порога (по умолчанию 3 %) — алерт и задача на
проверку таблицы цен.

## 11. Источники оплаты

### 11.1. Порт провайдера

По образцу `billing-provider.port.ts`, расширенно:

```ts
interface PaymentSource {
  id: 'paddle' | 'polar' | 'app_store' | 'google_play' | 'manual';
  capabilities: { checkout, customerPortal, offSessionCharge, proration, refundsApi };
  createCheckout(input): Promise<{ url }>;          // MoR
  verifyWebhook(req): Promise<RawEvent>;
  normalize(event): Promise<NormalizedEvent[]>;     // в наши события (§11.4)
  fetchSubscription(externalId): Promise<NormalizedSubscription>; // для сверки
  cancel / changePlan / pause …                      // где поддерживается
}
```

### 11.2. Merchant of Record

- **Paddle** или **Polar** — выбор на экземпляр; можно оба (рекомендация:
  Polar для `ivan-apps` — ниже комиссия, лицензионные ключи, удобный портал;
  Paddle для `bloggerdog` — зрелее в B2B: счета, НДС-номера, корпоративные
  клиенты).
- **Один аккаунт MoR — одно юрлицо.** TyCo и FastCat — два продукта в одном
  аккаунте, BloggerDog — свой аккаунт.
- Checkout — хостовая страница или оверлей MoR; `billingAccountId` передаётся
  в `custom_data`/`metadata` и проверяется в вебхуке.

### 11.3. App Store и Google Play

- Офферы: `Offer.source='app_store'|'google_play'`, `externalPriceId` =
  product id в магазине. Подписки — auto-renewable subscriptions; пакеты
  кредитов — consumables.
- Покупка только после входа в аккаунт. Связь с аккаунтом —
  `appAccountToken` (Apple) и `obfuscatedExternalAccountId` (Google) = UUID,
  выданный сервисом для `billingAccountId`.
- Приложение отправляет квитанцию / purchase token в `POST /v1/stores/{store}/purchases`;
  сервис проверяет её через App Store Server API / Google Play Developer API.
  Статус дальше ведут только серверные уведомления: App Store Server
  Notifications v2 и Google Real-time Developer Notifications (Pub/Sub).
- Consumable в Google Play подтверждается (`consume`) только после начисления
  кредитов; повторная квитанция идемпотентна по `transactionId`/`orderId`.
- **Конфликт источников:** если у аккаунта уже есть активная подписка на тот же
  тариф через другой источник, покупка блокируется на стороне приложения
  (`GET /v1/accounts/me/subscriptions` перед показом paywall) — двойную оплату
  магазины не возвращают автоматически.
- Внешние ссылки на оплату из приложения (где правила магазина это позволяют,
  например в США) — флаг на продукт и регион, по умолчанию выключен.
- Возвраты магазина приходят уведомлением (`REFUND`, `voided purchase`) и
  обрабатываются как возврат MoR (§8.8).

### 11.4. Нормализованные события

```
subscription.created | renewed | plan_changed | past_due | recovered |
  canceled (at period end) | expired | paused | resumed | refunded
payment.succeeded | refunded (cumulative) | chargeback
purchase.succeeded (pack/consumable) | refunded
```

Обработка: `BillingWebhookEvent` (уникальность по `(source, externalEventId)`)
→ очередь → нормализация → доменные действия в транзакции. События не по
порядку: каждая операция сравнивает `occurredAt`/версию и не откатывает более
новое состояние. Ежесуточная сверка (`fetchSubscription` по всем активным и
`past_due`) чинит пропущенные вебхуки.

## 12. Подписки

### 12.1. Модель

```
Subscription   id, accountId, planVersionId, offerId, source,
               externalSubscriptionId (unique per source), externalCustomerId,
               status, currentPeriodStart, currentPeriodEnd, trialEndsAt,
               cancelAtPeriodEnd, seats, pausedAt?, version
SubscriptionItem   subscriptionId, planVersionId (addon), quantity
Payment        как в BloggerDog: amount, fee, tax, discount, currency, kind,
               status, refundedAmountMicros (накопительно), source, externalId
```

Отличие от BloggerDog: у аккаунта может быть несколько подписок (по одной на
продукт плюс бандлы и дополнения), а не одна.

### 12.2. Статусы

Из `SubscriptionStatus` BloggerDog: `trialing → active → past_due → read_only →
expired`, `canceled` (оплачено до конца периода). Грейс-период `past_due`
настраивается на продукт (по умолчанию 7 дней). Повторные списания делает MoR
или магазин (у Apple/Google — свой billing retry и grace period, его статусы
маппятся на наши).

### 12.3. Даунгрейд и превышение лимитов

`downgrade.rules.ts`: смена тарифа вниз — в конце периода. Ресурсы сверх
новых лимитов не удаляются, а переходят в «только чтение» (политика задаётся
ключом права, см. §14 для диска).

## 13. Рефералы

### 13.1. Модель

Берём из BloggerDog `Partner`, `ReferralCode`, `ReferralClick`, `Referral`,
`ReferralCommission`, `PartnerPayout`, с изменениями:

- `Referral` привязан к `BillingAccount` (а не к организации) и к продукту
  атрибуции; реферер — любой пользователь (`Partner` с `tier='user'`), а не
  только одобренный партнёр.
- Добавлена `ReferralReward` — награда нефинансового вида.

```
ReferralProgram     id, productScope, termsVersion, rules (jsonb), status
ReferralReward      id, referralId, referrerAccountId,
                    kind: 'credits' | 'plan_grant' | 'commission',
                    productId, credits?, planVersionId?, durationDays?,
                    trigger: 'signup'|'first_payment'|'milestone'|'renewal',
                    status: 'pending'|'granted'|'void',
                    availableAt (холд против возвратов), idempotencyKey
```

### 13.2. Награды v1

- **Кредиты** — партия `referral` в кошельке продукта реферера. Приглашённому —
  приветственная партия.
- **Подписка** — грант тарифа (`PlanGrant`, §13.3) на N дней. Пример: «3
  оплатившихся приглашённых — месяц Pro», «10 — месяц Max».
- Награда начисляется после первой оплаты приглашённого и холда (по умолчанию
  14 дней, против возвратов и chargeback). Возврат в период холда — награда
  `void`; после выдачи — не отзывается (кредиты не забираем, грант
  дорабатывает).

### 13.3. Гранты тарифа

```
PlanGrant   id, accountId, planVersionId, source: 'referral'|'promo'|'manual'|'beta',
            sourceId, startsAt, endsAt, status
```

Грант даёт права и ежемесячное начисление кредитов, как подписка, но без
оплаты. Если у клиента уже есть платная подписка: права сливаются (§6.2) —
грант полезен, только если он выше. Чтобы награда не пропадала, грант на
тариф не выше текущего платного автоматически конвертируется в кредиты по
курсу, заданному в программе (`rules.fallbackCredits`).

### 13.4. Денежные выплаты (позже)

Таблицы `ReferralCommission` и `PartnerPayout` создаются сразу, начисления
комиссий пишутся со статусом `pending` при включённом флаге программы, но
выплаты (`PartnerPayout`) в v1 выключены. Правила из BloggerDog сохраняем:
комиссия от суммы за вычетом налога и комиссии MoR, отмена — только
отрицательной записью, ставка фиксируется на момент платежа, версия условий на
реферале. Альтернатива на будущее — партнёрка самого MoR.

### 13.5. Антифрод

- Атрибуция по коду при регистрации; самоприглашение запрещено (совпадение
  email-домена+устройства, платёжного метода по данным MoR, IP-подсети).
- Награда только после реальной оплаты, с холдом.
- Лимит наград на реферера в месяц; превышение — `review` в админке.

## 14. Дисковая квота

- Квота — право `storage.quota_bytes` (сумма тарифа и дополнений).
- Занятость — **измеряемый объём**, а не списание. Продукт (его сервер) сообщает
  `PUT /v1/storage/usage { accountId, productId, bytes, measuredAt }` после
  изменений и раз в сутки полным пересчётом.
- Перед загрузкой продукт вызывает `POST /v1/storage/reservations { bytes }` —
  резерв места, как для кредитов, чтобы параллельные загрузки не превысили
  квоту; после загрузки — commit фактического размера.
- Превышение (после даунгрейда или неоплаты): `over_quota` → синхронизация /
  загрузка только чтение → грейс 30 дней с уведомлениями → удаление по
  отдельному подтверждённому правилу продукта (сервис только сообщает событие
  `storage.retention_due`, удаляет продукт). Сроки — в настройках продукта.
- История занятости (`StorageUsageSnapshot`, ежедневно) — для аналитики и
  будущей оплаты по пику, если понадобится.

## 15. Онлайн-требование для TyCo

- Платные функции (облачные модели, синхронизация, облачный STT) требуют
  связи с сервером: все они физически идут через AI-шлюз и биллинг. Офлайн
  платные права не действуют.
- Токен прав — короткоживущий JWT (TTL 15 минут), подписан ключом экземпляра
  (JWKS по `/.well-known/jwks.json`), обновляется в фоне. Используется только
  для UI (показать, что доступно); решения о списании принимает сервер.
- Без сети TyCo работает только с локальными моделями. Локальные функции не
  требуют аккаунта и не проверяют подписку.

## 16. API

### 16.1. Типы клиентов

| Клиент | Аутентификация | Что может |
| --- | --- | --- |
| Сервер продукта / AI-шлюз | API-ключ продукта (`Authorization: Bearer`), привязан к `productId`, scopes | права, holds, usage, storage, создание внешних аккаунтов, checkout-ссылки |
| Приложение пользователя | OIDC access token | свой баланс, подписки, история, checkout, квитанции магазинов |
| Админка | сессия сотрудника + роли (`StaffRole` из BloggerDog) + аудит | всё, с записью в `AdminAuditLog` |
| MoR / магазины | подпись вебхука | вебхуки |

Ключ продукта не может читать или менять данные другого продукта, кроме
явно разрешённых кросс-продуктовых операций (гранты по правилу акции).

### 16.2. Основные эндпоинты

```
GET    /v1/accounts/:id/entitlements?product=tyco
GET    /v1/accounts/:id/balance?product=tyco
POST   /v1/credits/holds                 · /:id/commit · /:id/release · /:id/extend
POST   /v1/usage                         (событие без резерва: бесплатные/системные вызовы)
PUT    /v1/storage/usage                 · POST /v1/storage/reservations
POST   /v1/checkout                      { accountId, offerId | packOfferId, returnUrl } → { url }
GET    /v1/catalog?product=tyco&source=paddle&country=AR
POST   /v1/stores/:store/purchases
POST   /v1/accounts/external             (для экземпляров без модуля аккаунтов)
POST   /v1/referrals/attribution
POST   /webhooks/:source
```

Ошибки — коды из `BILLING_ERROR_CODES`, плюс `STORAGE_QUOTA_EXCEEDED`,
`SOURCE_CONFLICT`. Отказ из-за баланса — HTTP 402.

### 16.3. События продуктам

Сервис отправляет продукту подписанные вебхуки (outbox-таблица, повторы с
экспоненциальной задержкой): `entitlements.changed`, `balance.low`,
`subscription.*`, `storage.over_quota`, `storage.retention_due`. SDK
(`@billing/client`) проверяет подпись и сбрасывает кэш прав. Кэш прав в SDK —
60 секунд, плюс сброс по событию.

## 17. Веб: портал клиента и админка

**billing-web** (Nuxt, домен вида `account.<бренд>`):

- вход/регистрация (если модуль аккаунтов включён);
- страница тарифов продукта и checkout;
- баланс по продуктам, история списаний с разбивкой по функциям (из журнала —
  «куда ушли кредиты» без догадок), платежи и счета (ссылки MoR), управление
  подпиской (портал MoR), реферальная ссылка и награды, занятость диска.

Продукты открывают нужную страницу по ссылке с `product` и `returnUrl`; для
встраивания в интерфейс есть `@billing/client-vue` (баланс, paywall, кнопка
апгрейда) поверх пользовательского API.

**admin** (Nuxt): переносим разделы BloggerDog `money/*` (plans, credits,
subscriptions, payments, partners, overrides), `PlanVersionDiff`, impersonation,
аудит. Новое: каталог продуктов и реестров прав, офферы по источникам, цены
моделей и черновики из `pricing-sync`, сверка с провайдерами, дашборд маржи.

## 18. Надёжность и эксплуатация

- **Транзакции:** все изменения журнала, резервов и подписок — в транзакции
  Postgres; конкурентный доступ к кошельку — блокировка строки
  `(account, product)` в `credit_wallets`.
- **Outbox** для исходящих событий и писем; **inbox** (`BillingWebhookEvent`)
  для входящих.
- **Воркер (BullMQ):** обработка вебхуков, истечение резервов, сгорание
  партий, начисление по периодам, сверка с MoR/магазинами, сверка с
  провайдерами AI, `pricing-sync`, снимки занятости диска, рефералы (холды).
- **Метрики** (Prometheus, дашборды из `docker/metrics` BloggerDog): списания,
  отказы 402, задержка reserve/commit, отставание очереди вебхуков, расхождение
  сверок, **маржа по продукту/тарифу/модели**.
- **Предохранители:** глобальный дневной потолок себестоимости на экземпляр и
  на продукт; срабатывание — отказ в резервах и алерт.
- **Резервное копирование:** PITR для Postgres; журнал кредитов — критичные
  данные.

## 19. Безопасность и защита от злоупотреблений

- Ключи продуктов хранятся хэшем, ротация без простоя (два активных ключа).
- Подпись всех вебхуков (входящих и исходящих), защита от replay по времени.
- Бесплатный уровень: подтверждённый email до любых AI-трат
  (`AI_REQUIRE_VERIFIED_EMAIL`), лимит регистраций на устройство/IP,
  приветственные кредиты — после подтверждения.
- Лимиты частоты (rate limits) — отдельно от кредитов: кредиты — про деньги,
  лимиты — про злоупотребления и зацикленных агентов.
- BYOK (свой ключ провайдера) — право `byok.allowed`; вызовы с BYOK пишут
  `UsageEvent` с `costMicros=0` для нас и не списывают кредиты (возможна
  плата за платформу — правило продукта).

## 20. Персональные данные и удаление

- Удаление аккаунта из одного продукта (отзыв согласия, данные продукта) и
  удаление аккаунта целиком — разные операции.
- При полном удалении: обезличивание `Identity`; финансовые записи (`Payment`,
  журнал) храним обезличенными столько, сколько требует закон; у MoR — запрос
  на удаление через их API/поддержку.
- `ReferralClick` — только хэш посетителя (как в BloggerDog).

## 21. Экземпляры и юридическая сторона

- `ivan-apps`: TyCo + FastCat, модуль аккаунтов включён, один аккаунт MoR.
- `bloggerdog`: своя БД, свой аккаунт MoR, модуль аккаунтов выключен,
  BloggerDog подключается через S2S API как внешний продукт. Это даёт чистое
  разделение данных и денег для due diligence.
- **Права на код:** сервис — отдельный репозиторий, принадлежит автору; если
  BloggerDog станет отдельной компанией, она получает лицензию на сервис, а не
  владеет им. Решить до входа инвесторов.

## 23. Этапы

1. **Ядро.** Монорепо, `packages/core` с перенесёнными правилами и тестами,
   Prisma-схема: продукты, каталог, партии, журнал, резервы, права.
   S2S API: права, holds, usage. Админка: продукты, тарифы, кредиты вручную.
2. **Метеринг.** Таблица цен с векторами, `pricing-sync` с черновиками,
   интеграция с AI-шлюзом на `ai-kit`, дашборд маржи.
3. **Оплата через MoR.** Выбор Paddle/Polar, адаптер, checkout, вебхуки,
   сверка, портал клиента. Модуль аккаунтов + OIDC. Подключение TyCo.
4. **FastCat и дисковая квота.** Резервы места, политика превышения,
   дополнения.
5. **Рефералы v1.** Кредиты и гранты тарифа, антифрод, холды.
6. **Магазины.** App Store и Google Play: квитанции, серверные уведомления,
   конфликт источников.
7. **BloggerDog.** Отдельный экземпляр, перенос данных из его биллинга,
   переключение `ai-gateway` на S2S API, удаление старого модуля.
8. **Позже.** Денежные выплаты партнёрам, оплата диска по пику, внешние
   ссылки на оплату из мобильных приложений.
